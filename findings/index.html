Checks that cannot fail

Plant the defect a check claims to catch. If the suite stays green, the check is not a check.

Method

  1. Get the suite green and record the exact command and pass count.
  2. Plant ONE single-line semantic change in the source that a correct check must catch.
  3. Re-run. A survivor is the finding.
  4. Rule out an equivalent mutant: a change that leaves behaviour identical proves nothing.
  5. Report with the input, the wrong output, and the command that produces it.

A test that accepts both outcomes proves the code RUNS and never that it is CORRECT. Coverage cannot see this: the line executes. Only planting the defect can.

Two new assertion types: rouge-l and rouge-s

promptfoo/promptfoo#10256 · MERGED · +355/-129 across 17 files, 25.8k stars

promptfoo shipped rouge-n only. This adds summary-level ROUGE-Lsum and skip-bigram ROUGE-S, with their not- forms, through assertion dispatch, the configuration schema, CSV parsing and the eval creator.

The correctness hinge is sentence segmentation, which is why this is more than wiring a library. ROUGE-L and ROUGE-S split sentences BEFORE folding case; ROUGE-N tokenizes the whole text and can leave a mid-text period attached to the preceding word. Get that order wrong and identical text scores below 1.00, the one failure a scoring assertion must not have. The merged tests pin it: identical text scores 1.00 even when a token repeats, reordering whole sentences still scores 1.00 on rouge-l because each reference sentence is matched against every output sentence, and the same reorder scores below 1.00 on rouge-s because skip-bigrams span sentences.

Where I was wrong

I shipped a linter to PyPI that reported correct CI as broken, and the corpus average hid it.

deadgate 0.1.0, found by auditing Arize-ai/openinference

Three detectors asked whether a job reads its upstream's result using needs\.[A-Za-z0-9_-]+\., which cannot match '*', so the WILDCARD form GitHub documents was the one spelling the tool could not see. The finding's own text read 'never reads needs.*.result' while failing to match that string. On openinference, whose four CI gates each read it twice: 13 HIGH before, 1 after, and the survivor is unrelated. Corpus-wide the fix removes 43 of 430 HIGH, which is 9.1% against 92% on that one repository. The tool was least accurate on the repositories with the most careful CI, so no corpus average would have surfaced it. All 149 tests passed before and after, which is why there are 156 now. A fourth defect: the documented reproduction command for the published numbers raised NameError on three undefined names, so those figures came from a script that was never the one shipped.

My own fix was wrong in the other direction, and the mutation sweep is what caught it.

deadgate, the D4 gate-coverage check

To stop reporting jobs whose failure a fan-in gate already catches, I walked the needs graph transitively. That is unsound: needs.*.result reports only DIRECT needs, and a failed grandparent makes the parent SKIP, which is not a failure, so the gate never sees it. Transitive suppression would have silenced real findings. No test caught it; the mutation that DELETED the walk survived, and a surviving mutation that improves the program is evidence the program was wrong.
